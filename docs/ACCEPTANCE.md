# 受入条件・終了条件

このチェックリストは開発担当と独立レビュー担当の共通基準です。単なるループ回数やモデルの自信を完了判定にしません。対象候補の内容識別子、検査結果、指摘の根拠を記録してください。

## A. 全段階で満たす制約

- [ ] 追加課金を伴う操作がない。外部AI API、クレジット、支払い登録、プラン変更、課金付きクラウド実行を使用していない。
- [ ] 変更先はローカルの当該作業ツリーだけ。外部書き込みを行う場合も、別の許可された操作として `YutoOzawa/paper_app` のみに限定される。
- [ ] 他のリポジトリに変更、push、設定変更を行っていない。
- [ ] PDF、ページ画像、抽出全文、秘密情報、個人メモ、ローカル解析DBをGit・公開出力に含めていない。
- [ ] Google Drive連携、公開、課金、プラン変更、回復枠の自動使用を行っていない。
- [ ] 利用枠の残りが確認でき、対象の適用枠のどれかが5%以下なら新しい作業を開始せず、保存して停止している。
- [ ] 利用枠が不明・古い・取得不能な場合、都合よく残量があると仮定せず停止している。

## B. 準備物の受入条件（今回）

- [ ] 製品仕様、決定事項、AGENTS、実行・再開の説明が整合する。
- [ ] 実装→検査→独立したコードレビュー→独立したUI・内容レビュー→修正の順序が定義されている。
- [ ] 実装が変更できる範囲と、ハーネス・評価基準など変更してはいけない範囲が分かる。
- [ ] 回数、経過時間、各実行時間、進捗停止に上限があり、無限に再試行しない。
- [ ] 原子的な状態保存、異常終了からの再開、対象候補の変更検知を検証している。
- [ ] 残り5%以下・不明・失敗・ループ上限をテスト用の入力で確認でき、実課金や回復枠を使わない。
- [ ] 実際の利用状況を読み取れない実行経路では、手動の確認を要求するか停止する。テスト用データを本番の利用状況として受け入れない。
- [ ] テストや準備物の検証と、アプリ本体や実論文の完成を区別して報告する。
- [ ] エージェントに任意のシェル・ネットワーク・プラグインを公開せず、検査用ツールの入力を検証している。
- [ ] 標準環境は読み取り専用で、危険な機能と各MCPサーバーを明示的に無効化する。計画用ツール等まで全て消えているとは主張しない。
- [ ] 候補Nodeテストの読み取りはアプリ・テスト・アプリスクリプト・ルートpackage.json・test-tempだけ、書き込みはtest-tempだけで、子プロセスとネイティブアドオンを許可しない。
- [ ] 候補テストから信頼されたレポート・視覚証拠へ書けず、ホストの認証情報も読めないことを確認している。

## C. 機能実装の受入条件

### C1. 基本導線

- [ ] 会議→年→論文一覧→詳細の操作がPCとスマホ相当の幅で機能する。
- [ ] 新しい会議・年をデータで追加でき、既存のものを壊さない。
- [ ] タイトル・著者・所属・カテゴリ・公式バッジは要求された英語表記、説明は日本語。
- [ ] 原題、内容の一言説明、カテゴリ、ある場合の公式バッジが一覧で分かる。
- [ ] 日本語・英語検索、カテゴリ絞り込み、件数、検索なしの状態への復帰が機能する。
- [ ] 一覧から戻る、ブラウザの戻る／進む、前後の論文への移動で状態が不意に失われない。
- [ ] 未確認・未取得・データなし・通信失敗が正しく表示される。
- [ ] `app/index.html` と仕様のQAハッシュURLが検査の契約に従う。
- [ ] `?fixture=qa` のデータは架空の検査専用と明示され、本番データ・配信出力に含まれない。
- [ ] QAは通常のscriptとローカル検査データにより `file:` URLで動作し、ブラウザのファイル読み取り制限・CORSを無効化しない。

### C2. 読みやすさと操作性

- [ ] 実際に画面を表示して確認した証拠がある。コードだけで「読みやすい」と判定していない。
- [ ] 原題の長い論文、複数所属、多数著者、バッジなし、狭い画面を確認した。
- [ ] 主な操作にキーボードで到達でき、フォーカスが見え、クリックできる要素に適切な名前がある。
- [ ] 色だけに依存せず状態が分かり、文字の欠け・横方向の不必要なはみ出し・押せない操作がない。
- [ ] 初見の読者が詳細冒頭から「課題・難しさ・工夫・結果」を理解できる。
- [ ] 根拠や長い書誌情報が本文を圧迫せず、必要なときにはたどれる。
- [ ] 評価結果には条件が付き、専門用語や略語に必要な説明がある。

モデルによる読みやすさの評価は人間の理解を保証しません。レビューは代表的な表示と文章に対する具体的な観察を残し、主観的な好みだけで何度も作り直しません。

### C3. 保存と容量

- [ ] ブラウザを閉じて再開しても、同じ環境のお気に入り・既読が残る。
- [ ] 個人データの書き出し・読み込みが機能し、別端末への自動同期はないと分かる。
- [ ] 公開用データに個人データが混ざらない。
- [ ] 開発・解析の進捗が終了後も残り、保存済みの対象を再解析せず再開できる。
- [ ] 不完全な書き込みや破損状態を検出し、完了データを黙って失わない。
- [ ] ページを開いたときに不要な全会議の詳細データを取得しない。
- [ ] 配信出力、一時領域、ローカル保存の実測容量を記録する。
- [ ] 一時ファイルの上限と清掃経路を確認する。誤ったパスを再帰削除しない。

### C4. 安全な実装と検証

- [ ] 論文本文・外部メタデータを指示として実行しない。HTMLやスクリプトとして無条件に挿入しない。
- [ ] 外部リンクの危険なスキームや不正データで任意のコードを実行できない。
- [ ] 秘密情報をクライアントやGitに入れず、課金APIを呼ばない。
- [ ] 必須の動作・中断再開・データ検査を意味のあるテストで確認する。
- [ ] テストを弱める、無効にする、結果を捏造することで通過させていない。
- [ ] 存在するテストだけでなく、仕様の未実装項目も検査し、未実装を成功扱いしない。
- [ ] Chrome / Edgeの `--no-sandbox` は境界を確認したCodex OSサンドボックス内だけで使い、ホスト上で直接実行しない。ネットワーク禁止・check-work以外への書き込み禁止と通常のブラウザCORSを維持する。

## D. 実論文データの受入条件

### D1. 対象集合と公開年

- [ ] 各会議の正式な最新論文集の根拠URL・採用年・確認日がある。
- [ ] 公式の対象集合、対象件数、除外トラック、重複処理が説明できる。
- [ ] 全対象に安定IDと正しい書誌情報があり、取得不能な論文も残る。
- [ ] デモ・fixture・未確認のサンプルを実際の論文解説として掲載していない。
- [ ] `app/manifest.json` の5会議、各年、件数、`dataFiles`、完了状態が実データ・収集記録と一致する。

### D2. 1本ごとの品質

- [ ] 本文を読めた状態、使った版、取得元、確認日がある。
- [ ] 要旨だけの確認を全文分析済みと扱わない。
- [ ] 必須の説明項目があるか、本文に明記なし・未確認の理由が記録されている。
- [ ] 任意の「分野の課題」を無理に生成していない。
- [ ] 主要な主張、手法、数値、難しさについて節／ページ／図表の根拠をたどれる。
- [ ] 引用先の論文を読んだかのような説明をせず、対象論文内の記述に限定している。
- [ ] 日本語が簡潔で、誇張や重大な条件の省略がない。
- [ ] 著者・所属・カテゴリ・バッジが正しく、バッジの「なし」と「未確認」が区別される。
- [ ] 公式の個別論文ページへのリンクがあり、根拠なく組み立てたURLではない。
- [ ] PDF、抽出全文、論文図表の複製を永続データ・Git・配信物に含めない。

### D3. 完成の表示

機能実装の成功とコーパス完成は別のフラグで管理します。全対象論文がD1・D2を満たした場合だけ初期コーパス完成です。取得できないものが残る場合は件数・理由・次の手順を報告し、`partial` または `needs_human` 相当の状態にします。未取得をカウントから落として100%と表示してはいけません。

初期のオフラインループで実データを収集できない場合は `needs_data` とします。機能QAの架空データで撮った画面と、実論文の根拠を含めた本番レビューを区別します。`app/manifest.json` の `status: complete` は実論文の条件を満たす場合だけです。

初期エンジンは機能QAとレビューを完了しても、全体は `needs_data` で止めます。形式上の件数・収録状態 は整合性確認に過ぎず、実際の出典・本文・日本語の説明を対象にした後続レビューを置き換えません。

## E. レビューと自動ループの終了

レビュー担当は実装担当とは別の新しい実行コンテキストで、同じ候補を読み取り専用で評価します。コードレビューとUI・内容レビューの両方を行います。指摘には優先度、仕様・実行に基づく根拠、影響、修正を確認する方法を付けます。

| 優先度 | 意味 | 扱い |
| --- | --- | --- |
| P0 | 費用・情報漏えい・破壊・対象外リポジトリ変更など、直ちに止める重大問題 | 即停止または安全な封じ込め後に停止 |
| P1 | 主な操作の不能、データ消失、重大な誤表示や科学的誤説明 | 修正必須 |
| P2 | 仕様未達、重要な読みづらさ、再現する中程度の不具合 | 修正必須 |
| P3 | 主観的な微調整、軽微な改善提案 | 記録し、完了を不必要に遅らせない |

正常終了には、次の条件をすべて満たす必要があります。

1. 対象マイルストーンの全必須受入条件を満たす。
2. 必須の検査・テストが成功する。
3. 未解決のP0・P1・P2が0件である。
4. コードレビューとUI・内容レビューの双方が通る。
5. **変更のない同一候補に対して、連続2回、両レビューが通る。** 内容識別子が変わったら成功連続回数をリセットする。
6. 読めなかった本文、未実施の検査などを完了報告に含め、成果物の状態を正しく表す。

「指摘が同じだから終了」は採用しません。同じ重大指摘が残るなら修正失敗です。

ループは最大6サイクルです。全体の経過時間上限と各実行のタイムアウトも設定します。候補や指摘が改善しない状態が2回続く、上限に到達する、検査不能、利用枠が不明、残量5%以下などの場合は、成功とせず保存して止まります。時間切れや中断で欠けたレビューを成功に補完してはいけません。

停止報告には少なくとも以下を残します: 停止理由、成果の現在地、候補の内容識別子、済んだ検査、未解決事項、最後の利用枠確認、再開地点、次に行う操作。再開時は利用枠・対象リポジトリ・作業差分を再確認します。

## F. 公開は別判定

コードのGitHub保存とGitHub Pages公開を区別します。公開は現時点で承認済みではありません。自動ループはデプロイしません。将来公開する場合は、公開対象データ、私的情報、ライセンス・取得条件、容量、配信設定を確認し、公開の選択に応じた別の作業として行います。
