# Paper App — 製品仕様

この文書は2026年10月4日時点の相談を整理した実装仕様です。今回の準備作業はハーネス・指示・評価基準の作成までであり、アプリ実装や公開の完了を意味しません。後続の開発は、この仕様と `AGENTS.md`、`docs/ACCEPTANCE.md` に従います。

## 1. 目的

会議全体の研究を早読みし、読む論文を選ぶためのアプリを作ります。知らない分野でも「何が難しいのか」「何が新しいのか」「どの条件で役に立つのか」を簡潔に理解できることを重視します。各論文の精読を代替するものではなく、興味の入口と原論文への導線を提供します。

論文の説明は短くても理由と仕組みが分かるものにします。「性能が向上した」「従来手法を改善した」とだけ書いて済ませません。

## 2. 初期対象と拡張

- 初期会議: **SIGCOMM、INFOCOM、MobiCom、CVPR、NeurIPS**。
- それぞれ、収集時点で**本会議の正式な論文集が公開されている最新年**を対象とします。全会議が同じ年になる必要はありません。
- 採択発表のみ、開催予定、preprintのみの年を「正式公開の最新年」と扱いません。採用年・論文集のURL・確認日を記録します。
- 本会議の研究論文を対象にし、ワークショップ、デモ、ポスター要旨などを混ぜません。会議独自のトラック区分は公式情報で確認し、対象・対象外とその理由を記録します。
- 公式論文集の一覧を収録対象の基準とし、取得不能な論文も一覧から消しません。版違い・重複は安定したIDで整理します。
- 会議定義と年度ごとの論文データを分け、会議・年の追加で画面を書き直さずに済む構成にします。

初期5会議の全対象論文が最終的な収録目標です。少数の実データで画面を検証する段階と、全件の本文を分析する段階を分けます。試験データを用意しただけで、全件収録や製品完成を宣言してはいけません。

## 3. 表記と言語

| 情報 | 表記 |
| --- | --- |
| 論文タイトル | 公式の英語原題を保持 |
| 著者 | 論文・公式書誌の英語表記と順序を保持 |
| 所属 | 発表時点の英語表記。著者との対応を保持 |
| 分野・カテゴリ | 英語の統制されたタグ。複数付与可 |
| Artifact Badges | 公式の英語名称。出典も保存 |
| 要点・説明・解説 | 簡潔で読みやすい日本語 |
| アプリの操作表示 | 日本語を基本にし、固有名詞は公式表記を保持 |

所属が分からない場合は推測で埋めません。カテゴリは編集上の分類であり、公式分類と混同しないよう出所を区別します。論文タイトルを日本語訳に置き換えません。カードには別の情報として日本語の一言説明を付けられます。

## 4. 論文ごとにまとめる内容

1. タイトル
2. 著者
3. 大学・組織と著者の対応
4. 分野・カテゴリ
5. 内容の要約
6. 解いた課題
7. なぜ難しいか。従来手法で可能なこと、残る制約、この論文が扱う点
8. 貢献。著者の新規性の主張と、示された結果を区別
9. 手法。何をどう変えて課題に対処するか
10. 評価。データ・実験環境・比較対象・指標・主要結果・条件と限界
11. 今後の課題。著者が明記したものを優先
12. 論文内の説明から分かる分野の課題（**任意**。有用な根拠がなければ無理に作らない）

関連研究の調査は、対象論文のIntroduction、Related Work、本文などに書かれた説明に限定します。Referencesの書誌一覧だけから引用先の内容を想像しません。引用先を自動でたどって読む工程は今回の対象外です。

「本文に明記なし」「取得できず未確認」「AIによる解釈」を区別します。論文が主張していることを、独立に検証済みの事実として書きません。発表当時の課題と、現在も未解決だという主張も混同しません。

## 5. 読む分量と文章品質

- 一覧カード: 英語原題、40〜80字程度を目安とする日本語の一言説明、英語タグ、公式バッジ。
- 詳細冒頭: 「課題・難しさ・工夫・結果」が分かる200〜350字程度の日本語。
- 詳細全体: 説明本文は1,000〜1,600字程度を初期目安とし、論文の複雑さに応じて調整。
- 著者・所属・リンク・根拠は説明の文字数と別に扱います。

文字数は厳密な合否条件ではありません。必要な比較条件を削らないことを優先します。専門用語は初出で短く説明します。根拠のない称賛、過大な一般化、原文にない因果関係、数値の条件抜け、同じ説明の繰り返しを避けます。

## 6. 根拠と本文取得

要旨だけで全文分析済みにしません。合法的にアクセスでき、利用条件に適合する本文を読み、必要な図表と対象論文に付属する付録も確認します。図表を読み取れないなどの制約があれば記録します。利用できない有料本文は認証回避・購読・購入をしません。

書誌情報・分析に使った版・公式論文ページ・本文取得元・確認日・根拠の節／ページ／図表を保存します。本文の全ページ番号を決め打ちせず、実際の取得版に対応させます。根拠の詳細は折りたたみ等で普段の閲覧を邪魔しない形にします。

PDFは解析時にだけ少数ずつ一時取得できます。PDF、ページ画像、抽出した全文をGitHub・サイト・永続的な論文データに入れません。成功・失敗・中断時の一時ファイル清掃と起動時の残存確認を設け、対象パスを確認してから削除します。会議全体のPDFを先にため込む方式は採用しません。

処理状態の例: 一覧登録済み、本文取得待ち、本文取得不能、解析中、確認待ち、確認済み。実装で名前を変えても、未取得・未確認・完了の意味を潰してはいけません。

## 7. 公式リンクとArtifact Badges

優先するリンク先はPDF直リンクではなく、書誌情報・引用情報・本文への導線がある個別ページです。

- SIGCOMM・MobiCom: ACM Digital Library
- INFOCOM: IEEE Xplore
- CVPR: IEEE XploreまたはCVFの個別ページ
- NeurIPS: 公式論文集の個別ページ。正式版との対応が確認できる補助リンクを追加可

公式情報が見つからない場合は適切な代替とその理由を記録し、存在しないURLを組み立てて確定しません。

Artifact Badgesは論文に公式付与されたものだけ掲載し、例えば `Artifacts Available` と `Artifacts Evaluated — Functional` を同じ「認定済み」にまとめません。正式名称・付与元・確認URL・確認日を保存し、英語名と日本語での短い説明を表示できます。

バッジが確認済みで存在しない場合はカード表示を省略します。「なし」と「未確認」はデータ上区別します。コードの公開やGitHubリンクの存在だけで公式バッジを推定しません。独自にAIが確認した状態は、公式バッジと別の概念です。

## 8. 画面と主要操作

1. **会議選択**: 会議名、扱う領域の短い説明、収録状況。
2. **年選択**: 新しい年から表示。対象総数、分析済み件数、未分析を含む状態を表示。
3. **論文一覧**: 原題、日本語一言説明、英語カテゴリ、公式バッジが分かるカード。カードから詳細へ進む。
4. **論文詳細**: 要点、書誌、指定の説明項目、公式リンク、確認状況、必要時に開ける根拠。

主要機能:

- 日本語説明・英語原題・著者・カテゴリに対する検索。
- 分野タグでの絞り込み、件数表示。複数タグの重複集計を明示。
- あとで読む、お気に入り、既読管理。個人メモは必要な範囲で扱う。
- 一覧へ戻ったときの検索・絞り込み・位置の復元。
- 詳細から前後の論文へ移動。現在の絞り込み順を維持。
- キーボードで操作でき、スマホとPC双方で読めるレイアウト。
- 未取得・空の検索結果・破損データ・通信失敗を、空白画面にせず説明。

分野ごとの短い導入や年をまたいだ比較は将来候補です。今は複雑な管理画面、推薦の自動学習、ユーザー投稿、複数人共同編集を要求しません。

## 9. 保存、配信、容量

閲覧用は静的Webアプリとし、軽い文章データを会議・年・論文単位などで分割します。初回アクセスで全会議の全説明を読み込みません。課金されるAI APIやサーバーを閲覧のために呼びません。

開発・解析の進捗と完成した解説はディスク上に保存し、終了しても再開可能にします。公開用データと個人データを分離します。ブラウザ内のお気に入り・既読は再起動後も保持しますが、データ削除で消えることと、端末間では自動同期されないことを説明し、書き出し・読み込みを用意します。

GitHub Pagesを将来の公開候補とします。公開すれば端末を問わず同じURLで読めますが、URLを知る人だけに限定したアクセス制御ではありません。**公開は未決定で、自動デプロイは無効のまま**とします。研究室のサーバー、自前のグローバルIP、独自ドメインは不要です。

GitHub Pagesの上限を実装時に公式資料で再確認し、出力容量を計測します。PDFなしでも会議と年度が増えると容量は増えるので、上限直前まで無制限に追加しません。実測値と一時領域の使用量を示します。

**Google Drive連携は今回の範囲外です。** 認証・API・保存層を先回りして実装しません。必要なら開発後に別の変更として追加します。

## 10. 費用と外部への影響

追加課金は一切禁止です。契約済みのChatGPTに含まれるCodex利用枠でのみ開発・レビューを行います。AI API、従量制クレジット、課金付きクラウド実行、支払い登録、プラン変更、ドメイン購入、購読・論文購入を使いません。支払いが生じる可能性を確認できない処理は実行しません。

大量論文の解析が現在の無料・既存利用枠では終わらない場合は、保存して停止します。品質や対象を黙って縮小しません。自動取得は公式の許可された手段と制限に従い、間隔を空け、失敗時は待ち、完了済みの対象を繰り返し取得しません。

公開に法的リスクが一切ないとは保証しません。独自の簡潔な解説、原論文への参照、ライセンス表示、取得・利用条件の確認を設計に含めます。論文の大量転載やほぼ全文の翻訳を公開しません。

## 11. 到達点の区別

- **準備完了**: 本文書、AGENTS、チェック・再開・レビューを支えるハーネスが揃い、アプリ実装は未実施と報告する。
- **機能実装完了**: 実装の受入条件を満たす。実データの収録状況を別途明記する。
- **初期コーパス完成**: 5会議の正式公開最新年の対象集合が確定し、対象全件が要件どおり分析・確認される。
- **配信公開**: 別途ユーザーが公開を選んだ場合のみ。前3つの到達点から自動的に公開へ進まない。

取得不能・未解析が残る場合、部分的に使用可能なものは渡せますが、「全論文を分析済み」とは報告しません。

## 12. 初期実装と検査の契約

自動ループはローカルのCodex app-serverにChatGPTアカウントで接続します。このリポジトリを作業ルートとする読み取り専用の標準環境で、シェル、統合実行、アプリ、プラグイン、hooks、ブラウザ、標準画像表示、Web検索、設定済みの各MCPサーバーを明示的に無効にします。書き込みは役割ごとに許可された限定プロジェクト操作だけで行います。計画用などの副作用のない標準ツールは残る場合があります。導入済みCodexでは限定ツールのために `code_mode_host` が必要なので有効のままにし、`environments: []` は使いません。

信頼された検査は、ネットワーク禁止・check-work領域だけ書き込み可能と確認したCodexのOSサンドボックス内で行います。候補のNodeテストにはさらにNodeの権限制限を適用し、`app/`、`tests/app/`、`scripts/app/`、`package.json` とtest-tempだけを読み取り可能、test-tempだけを書き込み可能にします。子プロセスやネイティブアドオンを禁止し、信頼されたワーカーがテストを直接読み込みます。検査レポートと画像の保存先は候補テストに書き込ませません。

画面確認にはインストール済みChrome / Edgeを使い、ダウンロードしません。Windowsのサンドボックスの二重化が動作しないため、Chrome / Edgeの `--no-sandbox` は上記の検証済みCodex OSサンドボックス内だけで使います。無保護のホストでは使いません。ブラウザ本来のCORS等は無効にしません。

この初期ループには自動のインターネット取得を含めません。取得用アダプターを、保存済みの入力例に対して実装・テストすることはできますが、実際の論文収集は、利用条件と費用を確認した別の工程です。実データがない場合は `needs_data` などの明示的な状態で止め、製品全体を完成扱いしません。

アプリ実装時の固定エントリは `app/index.html` です。検査用表示では `?fixture=qa` を指定し、次のハッシュURLを使えるようにします。

- `#/conferences`
- `#/conference/SIGCOMM/2025`
- `#/paper/qa-paper`

QA用データは**架空の検査専用データ**と明示し、本番データと配信出力から除外します。検査用URLの2025という値はUIを確かめるための固定値であり、最新年の判断ではありません。架空論文の画面確認だけで本番の説明品質を認定してはいけません。

このQA表示は `file:` URLで動く通常のscriptとローカル検査データの読み込みを使い、ファイルへのfetchなどに対するブラウザの制限を緩めずに動作させます。`--allow-file-access-from-files` や `--disable-web-security` に頼ってはいけません。本番のHTTP配信では必要なJSONをfetchする構成を使えます。

`app/manifest.json` は最低限、次の情報を持ちます。

- `status`: `sample` または `complete`
- `conferences`: `{ id, year, officialIndexUrl, expectedPapers, listedPapers, analyzedPapers, unavailablePapers }` の配列
- `dataFiles`: `data/...json` の相対パスの配列

`complete` は対象集合が正式に確認され、対象全件の分析が確認済みの状態だけに使います。5会議の存在、対象総数・登録件数・解析件数・取得不能件数の整合、正式公開を確認した証拠を検査します。公式URLや件数が未確認の値の場合は完了を認めません。必要な詳細情報はマニフェストの追加項目や収集記録に保存します。

機能のQA成功後、実データが揃った段階で代表的な実論文の文章・画面・根拠について改めてレビューします。公開可能との判断は、そのレビューと公開の選択を経て行います。

初期の自動エンジンは機能の検査とレビューが通っても、実論文については `needs_data` で停止します。形式上の件数・収録状態 判定だけで製品全体の完成には進みません。実際の出典・本文・説明のレビューは独立した後続工程です。
